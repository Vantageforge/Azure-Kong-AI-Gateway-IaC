# Kong Gateway Configuration (APIOps with decK)

This directory is **config-as-code** for the data plane that `main.tf`
provisions: every Gateway Service, Route, Plugin and Consumer is declared
here as YAML and synced to Kong Konnect with [decK][deck], instead of being
clicked together in the Konnect UI.

It's deliberately a separate pipeline from the Terraform in the repo root.
Terraform answers *"does the AKS cluster and the Kong data plane node
exist"*; decK answers *"what does Kong do with the traffic that reaches
it"*. Different rate of change, different blast radius, different
reviewers — so they get different files and a different CI job
(`.github/workflows/kong-gateway-config.yml`).

[deck]: https://developer.konghq.com/deck/

## Why decK instead of the Konnect UI

The Terraform in this repo deploys Kong as a **Self-Managed Hybrid data
plane** (`admin.enabled = false` in `terraform.tfvars` — there's no Admin
API to talk to on the data plane pod). Konnect's control plane is the only
place Gateway Services/Routes/Plugins can be configured, and decK talks to
it directly over the same API the Konnect UI uses
(`deck gateway sync --konnect-token ... --konnect-control-plane-name ...`).
That gets Kong's request-handling logic the same guarantees the Terraform
already gives the infrastructure: reviewable diffs, a single source of
truth, and no configuration drift from someone clicking "Save" in a
browser during an incident.

The root README's Datadog section previously called out that the
`prometheus` and `opentelemetry` plugins had to be added by hand in the
Konnect UI, because plugin config is owned by Konnect, not the Helm chart.
`base/plugins/global.yaml` in this directory is that manual step, turned
into a file you can diff and review.

## Layout

```
kong-config/
├── base/                  # The actual config, split by concern
│   ├── services/          #   one file per Gateway Service
│   ├── routes/            #   one file per Service's Routes
│   ├── plugins/           #   one file per Service (+ a global.yaml)
│   └── consumers.yaml     #   API consumers + their credentials
├── environments/          # Per-environment values — see "Templating" below
│   ├── dev.env
│   ├── staging.env
│   └── prod.env
├── rulesets/
│   └── base.yaml          # `deck file lint` governance rules
├── scripts/                # render.sh / lint.sh / diff.sh / sync.sh
└── .rendered/              # generated by render.sh — gitignored
```

Services, Routes and Plugins live in **separate files under a shared
top-level `services:` / `routes:` / `plugins:` key**, cross-referencing
each other by name (Kong's flat declarative format, not the nested
`service.routes[].plugins[]` shape `deck gateway dump` produces by
default). That's what makes each piece reusable and independently
reviewable: `base/routes/users-api.yaml` doesn't need to know what plugins
`base/plugins/users-api.yaml` attaches to it, and a PR that only touches
rate limits only touches the plugins file. `deck file render` reassembles
all of it into one config before every diff/sync — see `scripts/lib.sh`
for the exact file list.

## Templating: one set of files, three environments

Every environment-specific value — upstream URLs, rate limits, the CORS
origin, credential secrets — is a `${{ env "DECK_..." }}` placeholder in
`base/**/*.yaml`, using [decK's own env-var substitution][env-vars]. There
is no separate templating engine (Jsonnet, Helm, gomplate) to learn: decK
does this natively, `deck file render --populate-env-vars` resolves the
placeholders, and every plugin config, timeout and rate limit that should
differ per environment is defined once in `base/` and parameterized from
`environments/<env>.env`.

[env-vars]: https://developer.konghq.com/deck/reference/env-variables/

```yaml
# base/plugins/users-api.yaml
- name: rate-limiting
  route: users-api-public-read
  config:
    minute: ${{ env "DECK_USERS_API_PUBLIC_RATE_LIMIT" }}
```

```bash
# environments/prod.env
DECK_USERS_API_PUBLIC_RATE_LIMIT=120
```

Add a fourth environment by copying `environments/dev.env` to e.g.
`environments/qa.env` and filling in its values — nothing in `base/`
changes.

**A note on quoting:** every templated field that's a *string* is
single-quoted in the source YAML (`url: '${{ env "..." }}'`), even though
decK's docs don't require it. `${{ env "..." }}` is a template that gets
textually substituted before the file is parsed as YAML — if the
substituted value happens to start with a YAML indicator character (a
literal `*` in `DECK_CORS_ALLOWED_ORIGIN`, notably), an unquoted scalar
parses as a YAML alias reference instead of a string and fails with a
fairly opaque error. Quoting sidesteps that entirely. Numeric fields
(`minute`, `allowed_payload_size`) are deliberately left **unquoted** —
quoting those would make decK see a string where Kong's schema expects an
integer.

### Reuse within a file: YAML anchors

`base/plugins/users-api.yaml` defines the public route's rate-limiting
`config:` block with a YAML anchor (`&standard_rate_limiting`) and the
admin route's plugin merges it (`<<: *standard_rate_limiting`), overriding
only `minute`. This is plain YAML, not a decK feature — it keeps the
"same policy shape, different limit" pattern from being copy-pasted, and
is the pattern to reach for any time two plugin instances in the same file
should stay in lockstep on everything but one field.

## Example entities in `base/`

Three services, chosen to show three different shapes of policy rather
than to be a real product catalog:

- **`httpbin`** — proxies `https://httpbin.org`, no auth. Exists so
  `make kong-diff-dev` and CI have something to sync against with zero
  setup, before any real upstream is wired in.
- **`users-api`** — one Service, two Routes with different plugin scoping:
  `users-api-public-read` (`GET`, rate-limited per-IP, no auth) and
  `users-api-admin-write` (`POST`/`PUT`/`PATCH`/`DELETE`, `key-auth` +
  its own tighter rate limit). Same Service-level `cors` plugin covers
  both.
- **`orders-api`** — `orders-api-crud` (customer-facing, `key-auth`
  required, `request-transformer` adds a header, `response-transformer`
  strips an internal one) and `orders-api-webhook` (`hmac-auth` instead of
  key-auth, for a partner-signed callback). Service-level `rate-limiting`
  covers both routes at once.

`base/consumers.yaml` defines the two consumers those plugins reference —
`internal-admin-console` (key-auth) and `partner-payments` (hmac-auth) —
with every credential value templated, never committed.

`base/plugins/global.yaml` has no `service:`/`route:`/`consumer:` key, so
it applies gateway-wide: `prometheus`, `opentelemetry` (wired to the same
in-cluster Datadog OTLP receiver `main.tf` stands up), `correlation-id`,
and `request-size-limiting`.

## Usage

```bash
# From the repo root (Makefile wraps all of these — see `make help`):

# Render the merged config for an environment. No credentials needed —
# safe to run locally or in any PR.
make kong-render-dev        # -> kong-config/.rendered/dev.yaml

# Lint it against rulesets/base.yaml.
make kong-lint-dev

# Preview what would change in Konnect. Needs credentials (see below).
make kong-diff-dev

# Apply it.
make kong-sync-dev
# make kong-sync-prod additionally requires CONFIRM_PROD_SYNC=yes —
# see scripts/sync.sh. In CI this is set automatically by the
# `sync-prod` job, which only runs via a manually-dispatched workflow run
# against the "prod" GitHub Environment.
```

Or call the scripts directly: `kong-config/scripts/render.sh <env>`,
`lint.sh <env>`, `diff.sh <env>`, `sync.sh <env>`.

### Credentials

`diff.sh` and `sync.sh` need a Konnect Personal Access Token and a control
plane name — these are secrets, so unlike everything else they're **not**
read from `environments/*.env`:

```bash
export DECK_KONNECT_TOKEN="kpat_..."               # Konnect → Personal Access Tokens
export DECK_KONNECT_CONTROL_PLANE_NAME="kong-aks-dev"
# export DECK_KONNECT_ADDR="https://eu.api.konghq.com"  # non-US region only

make kong-diff-dev
```

In CI these come from the GitHub Environment's secrets
(`KONNECT_TOKEN`, `ADMIN_CONSOLE_API_KEY`, `PARTNER_HMAC_USERNAME`,
`PARTNER_HMAC_SECRET`) and variables (`KONNECT_CONTROL_PLANE_NAME`) — see
the environment-specific jobs in
`.github/workflows/kong-gateway-config.yml`.

`scripts/lib.sh` also refuses to `diff`/`sync` staging or prod while any
of those three secrets are still the `changeme-in-ci` placeholder from
`environments/*.env`, so a forgotten CI secret fails loudly instead of
syncing a broken credential.

## CI/CD

`.github/workflows/kong-gateway-config.yml`:

| Trigger | What runs |
|---|---|
| Pull request touching `kong-config/**` | `render` + `lint` for dev/staging/prod (required check); best-effort `diff` against dev/staging if Konnect secrets are configured on the repo |
| Push to `main` | Auto-sync to **dev**, then **staging** |
| Manual (`workflow_dispatch`, `environment: prod`) | Sync to **prod**, gated by the `prod` GitHub Environment's required reviewers |

Prod is never synced automatically — only a manual dispatch against the
`prod` environment can trigger `sync-prod`, and that environment should
have required reviewers configured under **Settings → Environments** so
the actual approval happens there, not in this workflow's conditionals.

## Governance: `deck file lint`

`rulesets/base.yaml` enforces, at `error` severity (fails the PR check):
every Service/Route/Plugin instance must carry `tags`, and Service/Route
names must be lowercase kebab-case. At `warn` severity: tags should follow
an `env:`/`team:`/`domain:`/`kind:` convention, and Services should set an
explicit `connect_timeout` rather than relying on Kong's default. Add
rules here as the project's conventions grow — see decK's [lint
docs][lint] for the full rule syntax (`given`/`then`/`severity`,
JSONPath selectors, built-in functions like `pattern` and `defined`).

[lint]: https://developer.konghq.com/deck/file/lint/

## Extending this

**Add a Route to an existing Service:** add an entry to that service's
file in `base/routes/`, referencing the service by name
(`service: {name: <service-name>}`); add matching plugins in
`base/plugins/<service>.yaml` referencing the route by name
(`route: <route-name>` — note plugin-level `service`/`route`/`consumer`
references are a plain string, not `{name: ...}`, unlike the nested form
used inside `routes:` — decK's schema is inconsistent here and `deck file
render` will tell you immediately if you get it wrong).

**Add a Service:** new file in `base/services/`, `base/routes/`,
optionally `base/plugins/`, following the existing three as a template.
Nothing elsewhere needs to change — `scripts/lib.sh`'s `STATE_FILES` glob
picks up any file under `base/{services,routes,plugins}/`.

**Add an environment:** copy `environments/dev.env`, fill in real values,
done — `render.sh <name>` / `lint.sh <name>` / etc. all take the
environment name as their one argument and look up `environments/<name>.env`.
